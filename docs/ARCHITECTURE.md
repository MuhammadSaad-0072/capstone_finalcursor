# System design

## Architecture

```text
Browser (Next.js / React)
  ├─ market search + chart + indicators
  ├─ explanation and paper-trade UI
  └─ Supabase Auth session cookies
          │ same-origin JSON
          ▼
Next.js Route Handlers on Vercel
  ├─ input validation (Zod)
  ├─ market provider client + server cache
  ├─ deterministic indicators and fallback explanation
  ├─ optional Gemini API client
  └─ authenticated Supabase data access
          ├──────── Alpha Vantage (daily data/search)
          ├──────── Gemini API (selected market metrics only)
          └──────── Supabase Auth + Postgres (RLS ledger)
```

The browser never calls Alpha Vantage or Gemini directly. Provider keys are
read only by server code. Supabase's project URL and anon/publishable key are
also configured server-side. A Supabase service-role key is used only in the
server-side paper-trade write path and is never exposed to the browser.

## Data flow

1. Asset search calls `GET /api/market/search`. When an Alpha Vantage key is
   configured, the server requests ticker matches. Otherwise it searches a
   fixed demo catalog.
2. Selecting a symbol calls `GET /api/market`. The server fetches up to 100
   daily observations using the provider's compact daily-series response,
   caches that fetch for 30 minutes, calculates statistics and indicators, and
   returns source mode/provider/date. With no key it returns a generated
   synthetic series, explicitly marked as demo.
3. `POST /api/explain` accepts only a ticker. The server rebuilds market inputs
   and sends a narrow set of values to Gemini if configured. No email,
   password, transaction, or account detail is included. A Gemini key is used
   only when Supabase Auth is configured and the requester is signed in.
   Otherwise it produces a separately labelled deterministic rules explanation.
4. In configured mode, paper-trade requests require a valid Supabase user
   session. The API validates symbol/side/quantity, reads the server-side
   market close, then uses a server-only service-role client to call a Postgres
   function that can be executed only by `service_role`. The function checks
   available virtual cash or held quantity and inserts a ledger row
   transactionally. Reads are scoped by RLS to that user.
5. In unconfigured demo mode, the browser stores hypothetical trades in
   `localStorage`. The UI states that this data is local to that browser and
   does not claim it is database-backed.

## Indicator definitions

- **SMA(n):** arithmetic mean of the most recent `n` daily closes. SMA20 and
  SMA50 are `null` until enough observations exist.
- **RSI14:** 14-period Relative Strength Index calculated from close-to-close
  gains/losses. The first average gain/loss uses the first 14 changes; subsequent
  values use Wilder smoothing: `(previous average × 13 + current change) / 14`.
  A zero average loss yields 100 for a positive-only series and 50 for a
  completely unchanged series.

These indicators summarize historical prices. The interface does not map them
to trade recommendations.

## Database schema

### `auth.users` (Supabase-managed)

Supabase Auth owns account identity and password handling. The application
stores no password or separate profile table.

### `public.paper_trades`

| Field | Type | Purpose/validation |
| --- | --- | --- |
| `id` | `uuid` | Primary key generated by Postgres |
| `user_id` | `uuid` | References `auth.users`; owner of the ledger row |
| `asset_symbol` | `text` | Uppercase ticker matching the restricted ticker pattern |
| `side` | `text` | `buy` or `sell` |
| `quantity` | `numeric(20,6)` | Positive number of hypothetical shares |
| `price` | `numeric(20,6)` | Server-sourced daily close at record time |
| `created_at` | `timestamptz` | Server timestamp |

An index on `(user_id, created_at desc)` supports recent-history reads.
Positions, average cost, and virtual cash are derived from the ledger; no
duplicated positions table is needed. The SQL migration is
[`supabase/migrations/0001_initial_schema.sql`](../supabase/migrations/0001_initial_schema.sql).

RLS is enabled. Authenticated users may select rows only where `user_id = auth.uid()`.
Anonymous role grants and direct table inserts are revoked. The API verifies
the user's cookie-backed Supabase session, then calls a narrowly granted
`SECURITY INVOKER` Postgres function using a server-only service-role key. Only
`service_role` can execute this function; it checks the verified user ID,
paper position/cash, and writes the row within one transaction. The function
has an empty search path and no dynamic SQL. There is no client-supplied fill
price in this endpoint. Service-role access bypasses RLS, so the key must stay
server-side and the route must continue to verify the user before each write.

## API contract

Detailed request/response examples are in [API.md](./API.md).

| Endpoint | Purpose | Validation/auth |
| --- | --- | --- |
| `GET /api/market/search?query=` | Search supported symbols | Search length capped; provider errors returned without credentials |
| `GET /api/market?symbol=` | Daily history, source, stats, SMA/RSI | Ticker regex; Alpha key stays server-side |
| `POST /api/explain` | Explain the selected ticker's latest metrics | JSON body includes only a validated symbol; AI output is bounded to those inputs |
| `GET /api/auth/session` | Current user or demo mode | Session checked with Supabase Auth |
| `POST /api/auth/signup` | Create email/password account | Valid email; password 8–128 characters |
| `POST /api/auth/signin` | Sign in | Validated email/password; Supabase errors are not leaked |
| `POST /api/auth/signout` | Revoke session | Cookie-based Auth |
| `GET /api/trades` | Read up to 200 recent paper trades | Requires user in configured mode; RLS |
| `POST /api/trades` | Record hypothetical buy/sell | Auth required; symbol/side/positive quantity; server sets price; SQL checks cash/position |

## Security and failure handling

- **Secrets:** `.env.local` and Vercel server environment variables; no
  `NEXT_PUBLIC_` provider secrets or secret-bearing logs. The service-role key
  is used only by the authenticated server-side write path.
- **Authentication:** Supabase email/password sessions stored in secure
  framework-managed cookies. No authentication service is assumed in demo
  mode.
- **Authorization:** Postgres RLS protects user reads and rejects anonymous or
  direct authenticated inserts. The service-role key bypasses RLS and is
  strictly confined to one server-side insert function after session
  verification.
- **Validation:** API parameters and request bodies are validated server-side.
  Quantities must be positive and bounded; sells cannot exceed recorded
  holdings; buys cannot exceed virtual cash.
- **Data source and staleness:** each series returns its provider/demo label and
  latest observation date. Data older than five calendar days is flagged as
  potentially stale; no claim of real-time quotes is made.
- **External failures:** provider failures return a clear API error. Missing
  market credentials select synthetic demo mode. Missing Gemini credentials or
  AI failures select a visible rules-based fallback. No provider error silently
  becomes real-looking live data.
- **Logging:** errors use fixed event descriptions and do not log request
  payloads, credentials, email addresses, or provider URLs.
- **Abuse/quotas:** market requests are cached for 30 minutes; provider limits
  remain account-specific. Public deployment should enable Vercel's current
  request protection/rate-limiting controls before sharing API-backed routes.
- **Privacy:** the optional AI request contains only the selected asset and
  market values. It never includes credentials, account email, or trade history.
- **AI access:** the server requires a valid Supabase session before using a
  configured Gemini key. Without Supabase Auth, the route returns only the
  deterministic local explanation.

## Hosting and configuration

Vercel hosts the Next.js UI and Route Handlers. Supabase provides managed
Postgres/Auth. Alpha Vantage and Gemini are optional external APIs. Environment
variable names are listed in [`.env.example`](../.env.example); do not store
values in Git. Free-plan quotas and inactivity rules can change; check official
provider dashboards before a live presentation.
